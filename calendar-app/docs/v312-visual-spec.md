## 0. 结论摘要（先看这 8 条）

1. **裁切根因不是「格子太大」，是「可用空间被高估 24px」。** `.widget` 有 `padding: 12px`（widget.js:662），而 `availW/availH` 只扣了 `.pv-single` 的 `0.375em`，没扣宿主这 24px → em 几何比真实内容盒**宽高各恒定多 24px**（折合 0.26em @4×4 ～ 0.52em @1×1） → 固定 em 轨道必然溢出真实内容盒 → 底部末行被切。**修法不是改择优算法，是让 CSS 拥有格子尺寸。**
2. **采纳「JS 只决定列数、CSS 决定格子尺寸」的方向，但要做两处修正**：① 格子不能靠 `aspect-ratio`+`max-*` 保证正方形（会退化成矩形），必须由**单一 `--cell` 标量**同时定义行/列轨道；② 需要一个 `container-type: size` 的容器才能拿到 `100cqw/100cqh`（真实内容盒）→ 新增 `.pv-yg-body`。
3. **改造后「不裁切」是结构性保证，与真实卡尺寸无关**：格阵总尺寸 = `cols×cell + (cols−1)×gap ≤ 100cqw`，同理高度 ≤ `100cqh`，由 `min()` 的定义直接成立。JS 算错只影响「填不满 / 形状不好看」，**永远不影响「被裁」**。
4. **各规格目标行列数已定死**（见 §4 表）：年 = 2×2/4×4 用 20×19、2×4 用 29×13、1×FULL 用 44×9；月 = 7×5（1×FULL 16×2）；周固定 7×1；日 = 6×4 / 8×3 / 12×2。
5. **「年」不放弃「一年一格」**。2×2 上格边长 **25.9px（0.428em）**，是最小可接受值（0.30em = 18.2px）的 1.4 倍，完全够用；改 12 月份块会与 `.pv-yb-bars`（12 竖条）、`.pv-hy`（年热力图）**功能重复**。1×1 上 365 格只有 9.9px（不可用），但 yearGrid 原本就不在 1×1/2×1 的尺寸白名单里，无需处理。
6. **1×FULL「后半段加大一倍」的「后半段」已逐个定位**（见 §6）：dualZone=`.pv-dz-date`、ringClock=`.pv-rc-time`、stripeClock=`.pv-st-date`、wordClock=`.pv-wc-sub`、ringProgress=`.pv-rp-legend`。
7. **1×FULL「改左右结构」的左栏宽度上限 = 内容宽的 46%**，两栏 `space-between` 贴卡片左右边缘，禁止内容在 1387px 里居中漂浮。
8. **进度条组**：5 行在 2×4 用 1 列 5 行、1×FULL 用 2 列 3 行；百分比改**整数无小数**（`Math.round`），`.pv-mb-v` 宽 3.4em、`.pv-mb-k` 宽 2.2em（现值会把「生命」和「%」裁掉）；`STYLE_OPT_FIELDS.age/life` 默认改 **18 / 120**，`bars.def` 改 `y,m,w,d,life`。

## 1. 设计原则（本轮 5 条）

| # | 原则 | 具体化 |
|---|---|---|
| P1 | **格子恒正方形、恒不出轨道** | 由 `--cell` 单标量定义 `grid-template-columns` 与 `grid-template-rows`；`--cell = min(宽度解, 高度解, 上限)`，三值全部成立 |
| P2 | **填充率是软目标，裁切是硬禁止** | 宁可两侧留白（格阵居中），不可让格子越出内容盒；格边长设上限（`--cap`），避免大卡上出现「巨砖墙」 |
| P3 | **一个网格 = 一种粒度，形状由语义定，不由几何猜** | 月 = 7 列（周为行）、周 = 7 格一行、日 = 6×4 / 8×3 / 12×2（按卡宽高比）、年 = 近方形铺满 |
| P4 | **字号与尺寸随卡等比缩放，但比例常数不随卡变** | 同一粒度在 2×2 / 2×4 / 4×4 上的**格边长 : 卡宽**比例一致；圆角改用百分比（`20%`）而非 em，使 2×2 与 4×4 的圆角视觉一致 |
| P5 | **一切尺寸关系写进 CSS 变量，JS 只传整数与文案** | JS→CSS 的通道只保留 `--cols` / `--rows`（整数）+ 粒度类名（决定 `--gap`/`--cap`）；不再内联任何 `grid-template-*` |

断点由**卡规格名**驱动（宿主给尺寸名，不给断点），不引入 viewport 断点。同一粒度在 4 档下的**格边长 : 卡宽**比例恒定（差 ≤ 3%），因此不需要断点微调。

## 3. yearGrid 重构：CSS 拥有格子尺寸（核心）

### 3.1 现状问题（对应根因）

```
availW/availH = (卡像素 × scaleOk) / baseForAvail − 2×0.1875      ← 少扣宿主 24px
grid-template-columns: repeat(cols, Xem)                            ← X 算死，em 轨道
```
`X` 是 em 绝对值，与真实内容盒差 0.34–0.40em（2×2 上 ≈ 24px）→ 底部/右侧溢出被裁。

### 3.2 目标结构（DOM 三层）

```
.pv-yg                       display:flex; flex-direction:column; gap:0.30em;
  .pv-yg-head                flex:0 0 auto                （头部，见 §5）
  .pv-yg-body                flex:1 1 auto; min-height:0; container-type:size;
    .pv-yg-grid              （格阵，见 3.3）
```

### 3.3 CSS 契约（伪代码，非实现）

```
.pv-yg-body { container-type: size; }        /* 提供 100cqw / 100cqh = 真实内容盒 */

.pv-yg-grid {
  --cols: 20;  --rows: 19;                   /* JS 唯一通道：两个整数 */
  --gap: 0.10em;                             /* 按粒度 */
  --cap: 0.90em;                             /* 按粒度的格边长上限 */
  --cell: min(
      calc((100cqw - (var(--cols) - 1) * var(--gap)) / var(--cols)),   /* 宽度解 */
      calc((100cqh - (var(--rows) - 1) * var(--gap)) / var(--rows)),   /* 高度解 */
      var(--cap)                                                            /* 上限   */
  );
  display: grid;
  gap: var(--gap);
  grid-template-columns: repeat(var(--cols), var(--cell));
  grid-template-rows:    repeat(var(--rows), var(--cell));
  justify-content: center;  align-content: center;   /* 居中，留白比溢出好 */
  overflow: hidden;                                /* 兜底 */
}
.pv-yg-grid i { width:100%; height:100%; border-radius:20%; }   /* 不再用 aspect-ratio */
.pv-yg-grid.dot i { border-radius:50%; }
```

**为什么这样就永不裁切**：宽度方向总宽 = `cols×cell + (cols−1)×gap ≤ 100cqw`（`cell` 的宽度解参与 `min()`），高度同理 ≤ `100cqh`。`min()` 取小值时更安全。若 `--cap` 生效（`cell` 被压到上限），格阵反而**小于**内容盒 → 只留白、不溢出。

### 3.4 JS→CSS 通道重构（明确「谁负责什么」）

| 之前 | 之后 |
|---|---|
| JS 内联 `grid-template-columns/rows`（em 轨道） | **删除**。CSS 由 `--cell` 推导 |
| JS 内联 `--cols/--rows` | 保留，但**只传整数**；改由「粒度 + 规格名」的查表得出（§4），不再由几何择优 |
| JS 计算 `ygCellAt / ygLayout / ygPrefCols` | **删除几何择优逻辑**，只保留「按规格 × 粒度查 cols/rows」的查表函数 |
| `YG_HEAD_EM = 0.925` 常量 | **删除**。头部高度由 CSS 决定，格阵区用 `flex:1` 自动取剩余，JS 不再需要知道头部多高 |
| `YG_CELL_MAX = 3.0`（全局上限） | 改为**按粒度**的 `--cap`（年 0.90 / 月 1.60 / 周 1.15 / 日 2.00 em） |
| `YG_GAP = 0.1`（全局） | 改为**按粒度**的 `--gap`（年 0.10 / 月 0.16 / 周 0.14 / 日 0.16 em） |

**保留项**：`--cols`/`--rows` 变量名不变（向后兼容），但语义收紧为「整数计数」，不再是「几何结果」。

### 3.5 降级路径（必须写）

1. `container-type: size` 不可用（老 WebView）→ `@supports` 包裹的整块规则不生效 → 回落到**旧的 JS 内联 em 轨道**路径（但该路径必须先修 `availW/availH` 少扣 24px 的 bug，否则裁切复现）。
2. `cqh` 不支持 → 同上。
3. **无论走哪条路，`availW/availH` 都必须扣掉宿主 24px**：`availW = (w*scaleOk - 24)/baseForAvail - 2×FIT_PAD`（`24` = `.widget` padding 12×2）。这是**独立于重构的必修项**，即使最终全走 CSS 路径，也应先修（拼接模式的行数裁剪 `maxRows` 同样吃这个值）。

## 4. 分规格 × 分粒度目标表（本轮核心交付）

**读法**：`cols × rows` = JS 要传的 `--cols/--rows`；`cell` = CSS 算出的格边长（em + 设计基准 px）；`gap` = 该粒度的 `--gap`。px 值按「设计基准卡尺寸 + 该规格根字号」换算。

### 4.1 年（365 / 366 格）

| 规格 | cols × rows | gap | cell (em) | cell (px) | 覆盖率 W×H | 备注 |
|---|---|---|---|---|---|---|
| 2×2 | **20 × 19** | 0.10em | 0.4281 | **25.9px** | 98% × 100% | 近方形铺满，末行 5 格 |
| 2×4 | **29 × 13** | 0.10em | 0.5476 | **38.8px** | 98% × 100% | 高度受限，宽度略留白 |
| 4×4 | **20 × 19** | 0.10em | 0.6312 | **58.5px** | 100% × 100% | 与 2×2 同形状，格子随卡放大 |
| 1×FULL | **44 × 9** | 0.10em | 0.4624 | **23.9px** | 95% × 100% | 高度受限；备选 53×7（星期为行，20.3px，语义更佳但更稀） |

- **最小可接受格边长 = 0.30em**（2×2 上 18.2px）。低于此值 365 格退化为噪点，"今天"那格高亮失去意义（1×1 上 365 格只有 ≈9.9px，必须放弃）。
- 绝对下限 0.22em；**低于 0.30em 一律不排年格阵**。`yearGrid` 的尺寸白名单本就只有 `2x2 / 2x4 / 4x4 / 1xfull`，不进 1×1 / 2×1；1×1 与 2×1 上的"时间感"由 §8 的单日 / 倒计时类款式承担，**不要退回 365 格，也不要退化成 12 个月份块**（12 个月块与既有 `.pv-yb-bars` / `.pv-hy` 功能重复）。

### 4.2 月（当月 28–31 格）

| 规格 | cols × rows | gap | cell (em) | cell (px) | 覆盖率 | 备注 |
|---|---|---|---|---|---|---|
| 2×2 | **7 × 5** | 0.16em | 1.3890 | **84.1px** | 100% × 76% | 7 列 = 一周一行（周历语义） |
| 2×4 | **7 × 5** | 0.16em | 1.5357 | **108.9px** | 61% × 100% | 高度撑满，左右各留 3.7em 白 |
| 4×4 | **7 × 5** | 0.16em | 1.6000（触上限） | **148.3px** | 84% × 61% | `--cap:1.60em` 生效，防止巨砖 |
| 1×FULL | **16 × 2** | 0.16em | 1.4726 | **76.2px** | 100% × 63% | 超宽卡改「双排月条」，保持 7 列会只剩 28% 宽 |

### 4.3 周（7 格）

| 规格 | cols × rows | gap | cell (em) | cell (px) | 覆盖率 W | 备注 |
|---|---|---|---|---|---|---|
| 2×2 | **7 × 1** | 0.14em | 1.4062 | **85.1px** | 100% | 宽度撑满，高度仅 14% |
| 2×4 | **7 × 1** | 0.14em | 1.6000（触上限） | **113.4px** | 63% | 高度仅 19%，四周留白是 7 格的物理极限 |
| 4×4 | **7 × 1** | 0.14em | 1.6000（触上限） | **148.3px** | 83% | 高度仅 12% |
| 1×FULL | **7 × 1** | 0.14em | 1.6000（触上限） | **82.8px** | 46% | 高度 32% |

> **方卡 / 宽卡上「周」必然上下留白——这是 7 个格子的物理极限，不要靠拉成 4+3 两段去填。** 4+3 会破坏「一周七天」的语义连续性（4 格一段没有含义），且格子会被拉得更大（2×4 上 4+3 的 cell = min(2.677, 4.088) = 2.677em = 190px，比 113px 更大更糟）。
> **要填满方卡/宽卡，请改用已有样式 `weekGrid`（`.pv-wg2`，7 个竖条格按高度均分）**，那才是周信息的正确形态。年格阵的「周」只负责在横条语境下给一个紧凑的七天摘要。

### 4.4 日（24 格 = 24 小时）

| 规格 | cols × rows | gap | cell (em) | cell (px) | 覆盖率 W×H | 语义 |
|---|---|---|---|---|---|---|
| 2×2 | **6 × 4** | 0.16em | 1.6472 | **99.7px** | 100% × 71% | 每行 6 小时 |
| 2×4 | **8 × 3** | 0.16em | 2.0000（触上限） | **141.8px** | 89% × 76% | 每行 8 小时 = 一个班次 |
| 4×4 | **6 × 4** | 0.16em | 2.0000（触上限） | **185.4px** | 88% × 61% | 同 2×2 形状 |
| 1×FULL | **12 × 2** | 0.16em | 2.0000（触上限） | **103.5px** | 99% × 84% | 上/下午 |

> **12×2 vs 8×3 vs 6×4（2×4 超宽卡）**：选 **8×3**。理由：12×2 的行高被 24h÷12 的语义切成"上/下午"，但格子高度只剩 2 行（覆盖率 37% 高度），卡片上下空 63%；6×4 宽度只到 66%，左右空；8×3 在 2.34 的卡宽高比下两端都最饱满（89% × 76%），且"每行 8 小时 = 一个班次"仍是可读的语义。
> **1×FULL 选 12×2**：横条的天然形态就是一行 12 小时 + 一行 12 小时，99% 宽度铺满。

### 4.5 形状选择规则（JS 侧查表，替代几何择优）

JS 只做一件事：**按实测卡宽高比 A = 真实 w / 真实 h，在下表的候选形状里选覆盖率最高的那个**，然后只输出 `--cols/--rows`。

| 粒度 | A ≤ 1.25 | 1.25 < A ≤ 1.7 | 1.7 < A ≤ 2.6 | 2.6 < A ≤ 3.4 | A > 3.4 |
|---|---|---|---|---|---|
| 年 | 20×19 | 24×16 | 29×13 | 35×11 | 44×9 |
| 月 | 7×5 | 7×5 | 7×5 | 16×2 | 16×2 |
| 周 | 7×1 | 7×1 | 7×1 | 7×1 | 7×1 |
| 日 | 6×4 | 8×3 | 8×3 | 12×2 | 12×2 |

- 语义优先于几何：**月永远 7 列**（周为行）、**周永远 7 格一行**、**日只在候选集里选**。只有「年」允许随形状变化。
- 候选集之外不要新增形状；新形状必须先在 §4 的表里登记覆盖率数值。
- **`availW/availH` 不再用于挑形状**（它是被高估的），改用真实像素 `o.w / o.h`。

## 5. 头部行 `.pv-yg-head` 规格

现状：`font-size: 0.5em; line-height: 1.25`，`b` 仅加粗。

| 规格 | 头部字号 | 行高 | 头部块高（含 0.30em gap） | 左（标签） | 右（读数） |
|---|---|---|---|---|---|
| 2×2 / 4×4 | **0.375em** | 1.2 | 0.45em | 年份/周次，weight 700，`color: label3` | `297/365 天`，weight 800，`color: accent`，`tabular-nums` |
| 2×4 | 0.375em | 1.2 | 0.45em | 同上 | 同上 |
| 1×FULL | **0.5em** | 1.2 | 0.60em | 同上 | 同上 |

- 「天 / d」单位用 `<small>` 0.7em，跟随右读数（现有写法保留）。
- **头部不参与裁切**：`flex: 0 0 auto`，高度由内容决定；格阵区高度由 `flex: 1 1 auto` 自动取剩余 → 头部改字号不会挤坏格阵（这是删掉 `YG_HEAD_EM` 的前提）。
- 头部左右用 `justify-content: space-between`；标签与读数之间不要加固定 gap（靠 space-between 拉开），否则 1×FULL 上会被拉到两端造成"两坨孤岛"。
- 1×FULL 上头部 `font-size: 0.5em`（25.9px）是横条里唯一的小字锚点，1.6em 的时间大字必须靠它定"这是日期不是时刻"。

## 6. 1×FULL 改版方向（前半段 / 后半段）

1×FULL 几何：1386.88 × 346.72 px，根字号 **51.75px**，内容盒 **1350.0 × 304.8 px = 25.961 × 5.861 em**。
横条的通用构图原则（新增，**全局适用**）：

> **两锚点分布**：横条里所有「放大后半段」的样式，容器改 `justify-content: space-evenly`，让前半段落在卡的 1/4 处、后半段落在 3/4 处，中间的分隔元素落在正中。**不要把两块挤在中间**（那正是 v3.10/v3.11 反复修的"缩在中间一小块、四周大片留白"）。

### 6.1 后半段加大一倍（5 款）

### 6.2 改为左右结构（5 款）

**左右结构通则**：

- **左栏 = 主视觉**（数字 / 主体文字），**右栏 = 辅助信息**（状态 / 标题 / 日期）。5 款统一，不做例外。
- 左栏 `flex: 0 0 auto`，**宽度上限 = 内容宽的 46%（1×FULL 上 = 618px）**；右栏 `flex: 0 1 auto`，宽度上限同为 46%。容器 `justify-content: space-between` → **两块贴卡片左右边缘**，中间留白成为"沟槽"而不是"空洞"。
- 右栏内部：主文字与次文字上下堆叠（`flex-direction: column`），**右对齐**（`align-items: flex-end`）—— 右栏贴在卡片右缘，右对齐才不会在边缘留一道无意义的内缩。
- 垂直居中：两栏各自 `align-items: center`（块内），容器 `align-items: center`。
- 右栏字号 = 左栏主字号 × 0.28～0.45，且 **≤ 0.9em**（横条里超过 1em 的小字会喧宾夺主）。

## 7. 进度条组 `progress.multiBars`

### 7.1 语义与默认值

- 5 行：**年 / 月 / 周 / 日 / 生命**。
- `STYLE_OPT_FIELDS`：`bars.def` 由 `'y,m,w,d'` → **`'y,m,w,d,life'`**；`age.def` 由 `''` → **`'18'`**；`life.def` 由 `'85'` → **`'120'`**。
- 「生命」行百分比 = `age / life = 18 / 120 = 15%`。
- **百分比一律无小数**：`Math.round(v)`，`${n}%`。**禁止 `toFixed(1)`**（见 7.4 裁切分析）。

### 7.2 2×4（693.44 高，内容 643.8px = 9.068em）

| 规格 | 排布 | 行高 | 行间距 | 条高 | 标签字号 | 数值字号 | 合计高度 | 占比 |
|---|---|---|---|---|---|---|---|---|
| 2×4 | **1 列 × 5 行** | 0.95em | 0.62em | 0.60em | 0.60em | 0.66em | 5×0.95 + 4×0.62 = **7.23em**（513px） | 80% |

- 行内结构不变：`标签(左, 定宽) | 条(flex:1) | 数值(右, 定宽)`。
- 5 行在 693px 高里单列足够，不需要两列。

### 7.3 1×FULL（346.72 高，内容 304.8px = 5.861em）

| 规格 | 排布 | 行高 | 行间距 | 条高 | 合计高度 | 占比 |
|---|---|---|---|---|---|---|
| 1×FULL | **2 列 × 3 行**（5 项，末格空） | 0.90em | 0.40em | 0.60em | 3×0.90 + 2×0.40 = **3.50em**（181px） | 60%（余量用 `align-content: space-evenly` 均摊） |

- **每列宽 = (25.962 − 1.6em 沟槽) / 2 = 12.18em（630px）**；行内：标签 1.232em + 间距 0.4em + 条 flex + 间距 0.4em + 数值 2.108em → **条长 ≈ 8.04em（416px）**。

- **第 6 格空着是刻意的**；如果视觉上不能接受空位，改成 5 项按「年/月 | 周/日 | 生」排布（末格放"生命"并把它加宽），但仍保持 2 列 × 3 行的网格。
- `maxRows` 裁剪逻辑要改成二维：单列时 `maxRows = floor((availH + gap) / (rowH + gap))`，双列时 `maxRows = 2 × floor(...)`，且**只在真正放不下时才裁**，5 行在 2×4 / 1×FULL 上都不应被裁。

## 8. 1×1 与 2×1 新样式方案

前提：这两个尺寸**清空现有全部单卡样式**（`timeDate.dayNum` / `miniMonth` / `stackTime` / `stackBars` 等旧款下线，或作为内部实现复用但不再单列 chip）。
几何：
- **1×1 = 346.72 × 346.72**，根字号 46.23px，内容盒 **303.9 × 303.9 px = 6.606 × 6.606 em**（正方）。
- **2×1 = 346.72 × 693.44**，根字号 46.78px，内容盒 **306.6 × 654.9 px = 6.524 × 13.935 em**（窄高，宽高比 2.13）。

**窄高卡的排版铁律**：宽度只有 6.52em。**任何横排长文本都不可行** —— 0.75em 的中文一行最多 8 个字，1em 的大字最多 6 个字。窄高卡的样式必须是**纵向堆叠**（每行 ≤ 4 个字），或**单列超长数字**（如"23"占 1.23em，一行放得下 5 组）。
**方卡的排版铁律**：6.6em 见方里，最多放 **1 个主数字（≤ 3.4em）+ 2 行辅助（各 ≤ 0.6em）**。放第二组数字就会挤。

### 8.1 1×1 候选（4 款）

---

**① `timeDate.lunarDate` 农历日历块**

- **视觉构成**：主视觉 = 农历日（初一/廿三）2 字 **2.6em / weight 800**；辅信息 = 顶部「乙巳年 腊月」**0.44em / weight 700 / label3** + 底部「10月21日 周二」**0.42em / label2**。
- **排布**：三行竖排，居中，行间距 0.14em。总高 ≈ 0.57 + 2.6 + 0.57 ≈ 3.74em，在 6.6em 里上下各留 1.4em。
- **为什么适合 1×1**：农历日的字数是 1–3 字（"廿三"2 字、"初一"2 字），**方卡唯一能承载的"中文短词"信息量**，且 2.6em 大字在 346px 上 ≈ 120px，视觉重心成立。
- **与已有款的区别**：`dayNum` 是公历数字（阿拉伯数字），本款是**中文农历**；`miniMonth` 是整月网格，本款是**单日**。功能不重叠。

**② `timeDate.dayStack` 日时堆叠**

- **视觉构成**：主视觉 = 今日「日」**3.0em / weight 800 / accent**（tabular）；辅信息 = 左侧一列 4 个「时:分」读数（14 / 32 / 08 / 45），每行 **0.4em / tabular / label2**，行距 0.1em。
- **排布**：**左 68% 放 4 行时刻（占满 6.6em 高的 4/5），右 32% 放巨大「日」**。左右比例 2:1。
- **为什么适合 1×1**：把"今天第几天"和"今天第几时"两个信息叠进一个方卡，左右分栏让每个信息都有足够字号（主数字 3.0em = 139px）。
- **与已有款的区别**：`dayNum` 只有日期；本款加了**日内时刻的四个读数**（像飞行时钟的备份指示器），信息维度不同。

**③ `schedule.nextUp` 下一件事**

- **视觉构成**：主视觉 = 剩余时间「2:45:30」**1.9em / weight 800 / tabular**（时:分:秒）；辅信息 = 事件名「产品评审」**0.62em / weight 700 / label**（最多 4 字）+ 事件时间「今天 16:30」**0.44em / label2**。
- **排布**：主数字在上（1 行），事件名居中，事件时间在底。三行竖排，行间距 0.12em。总高 ≈ 2.4 + 0.8 + 0.6 = 3.8em。
- **为什么适合 1×1**：横排的「今天 16:30」在 346px 上放得下（0.44em × 8 字符 ≈ 1.4em），但事件名必须 ≤ 4 字。倒计时数字是天然的主角。
- **与已有款的区别**：`capsule` 是**年/月/周/日 的周期性倒计时**（胶囊描边 + 4 格），本款是**单条日程的精确剩余时间**（HH:MM:SS 连写）；`targetDay` 只算天数。

**④ `progress.dayRing` 日环进度**

- **视觉构成**：主视觉 = 一个 **3.4em 见方**的圆环（SVG，viewBox 0 0 100 100，r=44，stroke-width 7），环内是**已过比例的大字「63%」1.1em / weight 800**；辅信息 = 底部「今日 14:32」**0.44em / label3**。
- **排布**：环在上（3.4em），文字在下（0.6em），间距 0.16em，总高 ≈ 4.2em。
- **为什么适合 1×1**：346px 见方里，**圆是唯一能同时表达"环形 + 居中文字"的形状**；3.4em = 157px，环的线宽 7/100 × 157 = 11px，足够清晰。
- **与已有款的区别**：`ringProgress` 是**四条同心弧**（年/月/周/日 四层）；本款是**单环 + 环内大百分比**，只讲"今天"。
- ⚠️ **实现纪律**：环必须用 `viewBox` + `preserveAspectRatio` 默认 `xMidYMid meet`（**不要 `aspect-ratio` + `width:100%`**，见 §9），容器给固定 `width/height`（3.4em）。

### 8.2 2×1 候选（4 款）

---

**① `timeDate.tallClock` 竖向大钟**

- **视觉构成**：主视觉 = 巨大「14」**3.4em / weight 800 / tabular**，下面跟一个「:32」**1.5em / weight 700**（同基线右对齐，形成"主秒挂钟"感）；辅信息 = 底部一条 **0.16em 高**的当日进度条（0–24h）+ 条下「周二 10月21日」**0.42em / label3**。
- **排布**：从上到下 4 段：时分（3.4em + 1.5em 同行）→ 0.3em 间隙 → 进度条（0.16em）→ 日期（0.55em）。总高 ≈ 3.8 + 0.3 + 0.16 + 0.55 ≈ 4.8em，在 13.93em 里 → **上下留白各 4.5em 太多**。
- **修正后的排布（采用版）**：**时分放大到 5.2em / 秒 2.2em**，总高 ≈ 6.4 + 0.35 + 0.16 + 0.55 = 7.46em；上下各留 3.2em。此时主数字宽 = 2 × 0.616 × 5.2 = 6.4em **> 6.53em 内容宽（临界）** → 需 `letter-spacing: -0.04em` 收 0.4em → 6.0em ✓。
- **为什么适合 2×1**：竖高卡的核心优势就是**一个数字可以做到很大**（5.2em = 243px，是 1×1 的 1.75 倍）。这是 2×1 唯一不可替代的用法。
- **与已有款的区别**：`stackTime` 是**时/分/秒 三行等权重**；本款是**一个超大主数字 + 次级秒**，层级完全不同。

**② `schedule.verticalList` 纵向日程表**

- **视觉构成**：主视觉 = **3 条日程**的纵向列表，每条 = 左侧时间「09:00」**0.46em / tabular / label3** + 右侧事件名「晨会」**0.56em / weight 700 / label**，行间用 **0.06em** 的 `currentColor @ 12%` 横分隔线；辅信息 = 顶部「今日 3 项」**0.42em / label3** + 底部「下一项 14:00」**0.42em / accent**。
- **排布**：顶部标签 → 3 行列表（每行 0.8em）→ 底部 next 行。总高 ≈ 0.55 + 3×0.86 + 0.55 ≈ 3.7em。**仍然只占 13.93em 的 27%** → 需要放大：每行提到 **1.15em**、事件名字号提到 **0.72em**、行距 0.1em → 总高 ≈ 0.7 + 3×1.35 + 0.7 = 5.45em。
- **为什么适合 2×1**：窄高卡**唯一能容纳"多行短文本"**的形态（每行 ≤ 4 字），并且纵向列表与卡片的纵向节奏同向。
- **与已有款的区别**：拼接模式的 `schedule.multiple` 是横向多行（每行"名 + 右对齐时间"），本款是**竖向、左侧时间右侧名**的表格式，且只在 2×1 单卡出现。
- ⚠️ 若要填满 13.93em，应支持 **4–5 条**（而不是固定 3 条）—— 条数由高度决定：`条数 = floor((availH − 1.4em) / 1.35em)`。

**③ `timeDate.weekColumn` 竖向星期条**

- **视觉构成**：主视觉 = **7 行**（一~日），每行 = 星期字「一」**0.52em / weight 700** + 该日的日期数字「21」**1.1em / weight 800 / tabular**，今天那行整行用 accent 色块（`background: accent; color: #fff`）；辅信息 = 顶部「第 42 周」**0.44em / label3**。
- **排布**：顶部 0.6em + 7 行 × 1.5em = 11.1em → 12.3em / 13.93em ✓（留 0.8em 上下）。
- **为什么适合 2×1**：一周是**天然纵向序列**（7 行），竖高卡把"周"从一排 7 格（横向条）翻转成 7 行 → 每行能给到 1.1em 的日期数字，**在 346px 宽度下不挤**（1.1em = 51px 数字 + 0.52em 星期字）。
- **与已有款的区别**：`weekGrid`（`.pv-wg2`）是**横向 7 格**；本款是**纵向 7 行 + 大日期数字**，是同一信息的不同排布。

**④ `progress.lifeBar` 生命刻度尺**

- **视觉构成**：主视觉 = 一条**竖向刻度尺**：20 个刻度块（每块 0.28em 高、0.06em 间距），已过的块用 accent 填充到当前年龄，第 10 块上方标「18」，末端标「120」；辅信息 = 顶部「生命进度 15%」**0.52em / weight 700** + 底部「已过 18 年 / 预计 120」**0.42em / label3**。
- **排布**：顶部标签 0.7em + 刻度尺 20×0.34 = 6.8em + 刻度标注 0.5em + 底部 0.55em ≈ 8.55em / 13.93em。
- **为什么适合 2×1**：竖向刻度尺是**唯一能把"18/120"这种稀疏比例画得好看**的形态（横向 120 格会挤成一条线，竖向 20 格可以每 5 格标一次）。
- **与已有款的区别**：`multiBars` 的「生命」行是**一行百分比**；本款是**把生命跨度本身画出来**（每格 ≈ 6 年）。
- ⚠️ 这是 `progress.multiBars` 的"生命"行的**独立放大版**，两者不同时出现在一张卡上（内容互斥）。

## 9. 明确「不建议改」清单（避免返工）

| # | 不要做 | 原因 |
|---|---|---|
| N1 | **不要用 `position: fixed`** 做格阵/图例定位 | 脱离卡内裁切层，会溢出到宿主面板的相邻卡片 |
| N2 | **不要用 `aspect-ratio` + `width: 100%`** | 本项目已踩坑：宽扁卡上顶出卡片、竖高卡上把图例挤出内容盒（见 `.pv-rc-ring` 注释）。环/表盘一律 `viewBox` + `preserveAspectRatio` |
| N3 | **不要用 `flex:1 + min-height:0` 的百分比高度链**去撑 SVG | 宿主不给确定高度时整条链塌成 0，SVG 变 0×0 不渲染（用户报"指针不显示"即此因） |
| N4 | **不要保留 JS 内联的 `grid-template-*`** | 一旦 JS 也写轨道、CSS 也写轨道，两个真源打架 → 回到"算死 em 轨道 → 溢出被裁"的原点 |
| N5 | **不要保留 `YG_HEAD_EM` 之类的"预测头高"常量** | 头高由 CSS 决定，格阵区用 `flex:1` 取剩余；保留常量 = 保留一次裁切源 |
| N6 | **不要用 `aspect-ratio` 保证格阵正方形** | 轨道是 1fr 时格子天然填满轨道；要正方形必须由 `--cell` 单标量同时定义行/列轨道（见 §3.3） |
| N7 | **不要在 lit 模板里出现未转义的反引号** | 反引号是 `html`/`css` 模板结束符，会整页白屏只剩 "NaN" |
| N8 | **`<svg>` 片段必须用 lit 的 `svg` 标签函数** | 用 `html` 会创建 HTML 命名空间元素，尺寸恒 0、完全不渲染 |
| N9 | **不要用 `toFixed(1)` 输出百分比** | 6 字符实宽 > 定宽框 → `%` 被裁（用户截图已确认） |
| N10 | **不要把 `.pv-mb-k` 宽度留在 1.7em** | 「生命」两字 = 1.12em 根 > 0.95em 根 → 被裁 |
| N11 | **不要在 1×FULL 用 `flex-wrap` 让 5 行进度条压成两行** | 压成两行后行内"标签 + 条 + 数值"被压到 50px 宽的条 → 溢出。正确解是 2 列 × 3 行（§7.3） |
| N12 | **不要把「周」拆成 4+3 两段填宽卡** | 破坏"一周七天"语义，且格子反而更大（见 §4.3 注） |
| N13 | **不要在窄高卡（2×1）用横排长文本** | 6.52em 宽，0.75em 中文一行仅 8 字 |
| N14 | **不要执行任何 git 写操作** | 本轮只读文件 + 出规格 |
| N15 | **改 `.pv-single-*` 的根字号时必须同步 `SINGLE_BASE_PX`** | 两处不同源 → 预览与实际字号不一致（CSS 注释已注明） |

## 11. 遗留风险与待确认

1. **宿主是否保证卡片尺寸 = 设计基准尺寸**？本规格的所有 px 值按"宿主给的 = 设计基准"计算。若宿主给的比例不同（如 2×4 实际是 1600×700），**em 口径全部有效、px 口径失效** —— 因此落地时**优先用 em 口径**（§4 表里 px 只是"当前基准下的换算"）。
2. **`.widget` 的 24px padding 是硬编码在 widget.js 的 CSS 里**（`padding: 12px`）。若宿主主题改了 padding，`availW` 的修正量要跟着改 → 建议把 24 抽成一个常量并与 CSS 同源。
3. `container-type: size` 在极老 WebView 上不可用 → 走 §3.5 的降级路径（**降级路径也必须先修 24px 的 bug**）。
4. 「生命」行的语义（18 / 120）是**用户可配的默认值**，不是硬编码；条形百分比仍取 `age/life`。
